# ภาพรวมระบบใบลา ระบบข้อมูลสนับสนุน และ warehouse

เอกสารประกอบบทความฉบับขยาย 6 หน้า สรุปจากโค้ดที่ตรวจวันที่ 15 ตุลาคม 2569 ไม่ใช่ผลทดสอบการติดตั้งจริง

## หน้าที่ของแต่ละส่วน

| ส่วน               | ข้อมูลหลัก                                          | หน้าที่                                                  |
| ------------------ | --------------------------------------------------- | -------------------------------------------------------- |
| ระบบใบลา           | บัญชี นิสิต คำขอ ขั้นอนุมัติ snapshot และการรับทราบ | รับคำขอ ตรวจสิทธิ์ ตัดสินตามลำดับ จัดการหลักฐานและเอกสาร |
| ระบบข้อมูลสนับสนุน | รายวิชา ตอนเรียน ผู้สอน ที่ปรึกษา–นิสิต             | จัดการข้อมูลอ้างอิง นำเข้า Excel และให้บริการค้นหา       |
| warehouse v2       | มิติ ข้อเท็จจริง ความสัมพันธ์ และ batch             | รวมข้อมูลรายงานโดยคงหน่วยการนับและความสดของข้อมูล        |

## การเชื่อมต่อที่ตรวจพบ

1. ระบบใบลาตั้งปลายทาง ระบบข้อมูลสนับสนุน ผ่าน `LEAVE_REQUEST_COMPONENT_API_URL` แล้วเรียกตัวเลือกวิชาและตอนเรียน/ผู้สอน ข้อมูลที่เลือกใช้ประกอบรายละเอียดใบลาและ snapshot
2. บริการตรวจสิทธิ์และรายงานเรียกรายชื่อนิสิตในที่ปรึกษา และวิชา/ตอนเรียนปัจจุบันของผู้สอน โดยระบุตัวบุคคลจาก session และบริการบุคลากร
3. ตัว capture สำหรับ ETL อ่านฐานใบลาและ snapshot ร่วมกับข้อมูลบุคลากรและ ระบบข้อมูลสนับสนุน เพื่อประกอบ reference manifest โดยเก็บตอนเรียนที่ไม่มีการลาในเทอมปัจจุบันเมื่อมีข้อมูลต้นทาง
4. Extract อ่านต้นทาง, Transform ตรวจรหัสและ mapping, Load เขียน warehouse ในธุรกรรมเดียว พร้อมตรวจคุณภาพและบันทึก batch
5. บริการ `warehouse-dashboard/live/:report` อ่านข้อมูล `dw_*` แล้วจำกัดตามบทบาทและความสัมพันธ์ปัจจุบัน ก่อนส่งให้หน้าเว็บรายงาน API เก่าเลิกใช้ตามสถานะใน README โครงการ

ชื่อเส้นทางข้างต้นใช้สำหรับระบุจุดเชื่อมในซอร์ส ไม่ใช่คู่มือเรียก API ที่ผ่านการทดสอบสด

## โครงสร้าง ระบบข้อมูลสนับสนุน

| ตาราง                       | ความหมายและข้อกำหนด                                                                       |
| --------------------------- | ----------------------------------------------------------------------------------------- |
| `subjects`                  | รหัสวิชาไม่ซ้ำและชื่อวิชา                                                                 |
| `subject_sections`          | ตอนเรียนของวิชา ตารางสอนแบบข้อความและ JSON; คีย์ไม่ซ้ำรวมวิชา ตอนเรียน และข้อความตารางสอน |
| `subject_section_lecturers` | ผู้สอนแต่ละตอน; คีย์ไม่ซ้ำรวมตอนเรียนกับรหัสผู้สอน                                        |
| `advisor_student`           | ที่ปรึกษา รหัสนิสิต และภาควิชาแบบข้อความ; รหัสนิสิตไม่ซ้ำ                                 |

มีหน้าจัดการและค้นหา พร้อมบริการเพิ่ม แก้ไข ลบ และนำเข้า Excel แยกรายวิชากับที่ปรึกษา การตอบรหัส BigInt ใช้ข้อความ สคีมานี้ไม่มีตารางภาคการศึกษาหรือหลักสูตร และไม่ใช่ฐานทะเบียนลงเรียนรายนิสิตที่ครบทุกมิติ

การนำเข้าแบบเพิ่มข้ามรายการซ้ำตามคีย์ จึงไม่ใช้แทนการเปลี่ยนที่ปรึกษาของรหัสนิสิตเดิมโดยอัตโนมัติ แบบแทนที่ล้างข้อมูลชุดเดิมก่อนธุรกรรมเขียนข้อมูลใหม่ โค้ดที่ตรวจจึงไม่ให้หลักฐานว่าขั้นล้างและขั้นเขียน rollback ร่วมกันได้ ต้องแยกประเด็นนี้จากการโหลด warehouse ที่ใช้ธุรกรรมเดียว

## หน่วยการนับของ warehouse

| ตาราง                              | หนึ่งแถวหมายถึง                 | การใช้                           |
| ---------------------------------- | ------------------------------- | -------------------------------- |
| `dw_fact_leave_request`            | หนึ่งคำขอจากระบบต้นทาง          | จำนวนใบลาและผลรวมวันลา           |
| `dw_fact_leave_subject`            | หนึ่งคำขอและหนึ่ง offering      | รายวิชา/ตอนเรียนที่ได้รับผลกระทบ |
| `dw_fact_approval_step`            | หนึ่งขั้นอนุมัติจากต้นทาง       | ผลตัดสินและระยะเวลาการพิจารณา    |
| `dw_bridge_leave_subject_lecturer` | หนึ่งคำขอ offering และผู้สอน    | ผู้สอนร่วมและเวลารับทราบ         |
| `dw_snapshot_student_term`         | สังกัด/ที่ปรึกษาของนิสิตตามเทอม | บริบทการวิเคราะห์ที่มีหลักฐาน    |

มิติหลักได้แก่นิสิต บุคลากร ปี/ภาคการศึกษา ประเภทลา คณะ ภาควิชา หลักสูตร วิชา และ offering การรับทราบของผู้สอนไม่ใช่ขั้นอนุมัติ และข้อมูล roster สำหรับรายงานย้อนหลังไม่ใช่หลักฐานสิทธิ์ปัจจุบัน

ตัวอย่าง: 1 ใบลา 3 วัน กระทบ 2 วิชา มีผู้สอนร่วม 3 คน ต้องยังนับเป็น 1 ใบ 3 วันเมื่อสรุประดับคำขอ ไม่รวมวันซ้ำจากแถววิชาหรือผู้สอน และไม่ใช้ `SUM(DISTINCT request_days)` เพราะใบลาต่างกันอาจมีวันลาเท่ากัน

วันลาในปฏิทินกับวันขาดเรียนจริงเป็นคนละตัวชี้วัด ค่าเฉลี่ยตามเทอมรวมเทอมที่ไม่มีการลา ส่วน box plot ผู้สอนใช้ยอดรายวิชาต่อเทอม ระยะเวลาพิจารณาต้องมีหลักฐานเวลาเปิดขั้นและเวลาตัดสิน ค่าที่ขาดคงเป็น NULL

## การโหลดและคุณภาพข้อมูล

ETL ปัจจุบันเป็น full snapshot ในหน่วยความจำ ไม่ใช่ incremental/CDC ค่าเริ่มต้น CLI เป็น dry-run การโหลดจริง upsert ตาม identity ต้นทางและ sync ข้อมูลลูก การ reconcile จัดการข้อมูลที่หายจาก snapshot ครบชุด มี single-writer lock และ commit ข้อมูลพร้อมสถานะสำเร็จของ batch หากผิดพลาด rollback ข้อมูลและบันทึกความล้มเหลว

ต้องตรวจรหัสเป็นข้อความ ความสอดคล้องของภาคการศึกษา และ aliases ของรหัสบุคลากรกับบัญชี ไม่เดาภาควิชาเจ้าของรายวิชาจากสังกัดนิสิต หรือเดาหลักสูตรจากสัดส่วนจำลอง คลังข้อมูลไม่ควรเก็บเหตุผลสุขภาพ หลักฐาน และข้อมูลติดต่อที่ไม่จำเป็นต่อรายงาน

ข้อมูลเจ้าของวิชา ภาควิชา หลักสูตร และเวลาพิจารณาบางรายการยังไม่ครบตามเอกสารโครงการ รอบ refresh อัตโนมัติยังต้องกำหนด ชุดข้อมูลใน batch อาจเก่ากว่ารายชื่อผู้มีสิทธิ์ปัจจุบัน จึงตรวจสิทธิ์จากต้นทางขณะเรียกบริการรายงาน

## กรณีที่ควรเก็บผลทดสอบเพิ่ม

- ระบบข้อมูลสนับสนุน: อ่านข้อมูลแบบแบ่งหน้าและค้นหา, ตารางผู้สอนร่วม, นำเข้าซ้ำ, โหมดเพิ่ม/แทนที่, เปลี่ยนที่ปรึกษาเดิม และข้อมูลตารางสอนไม่ครบ
- การเชื่อมระบบ: บริการอ้างอิงล้มเหลว, เปลี่ยนความสัมพันธ์ปัจจุบัน, ความตรงกันของรหัสบุคคล และ snapshot ที่ส่งแล้ว
- warehouse: rerun, เปลี่ยนข้อมูลลูก, rollback, reconcile, ป้องกันการโหลดพร้อมกัน และข้อมูล mapping/timing ไม่ครบ
- รายงาน: หนึ่งใบหลายวิชา/ผู้สอน, เทอมไม่มีใบลา, สิทธิ์ต่างบทบาท, ขอบเขตปัจจุบัน และเวลา batch สำเร็จล่าสุด

งานเอกสารรอบนี้ไม่ได้รันกรณีเหล่านี้หรือแก้ข้อมูลในบริการจริง
